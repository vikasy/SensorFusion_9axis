## Critical Bug Identified

### The Sign Error

**Problem:** Accelerometer Z-axis has **opposite sign** compared to synthetic datasets.

**Evidence:**

#### Sample 0 (Identity Quaternion, Stationary)

**Realistic walking.csv:**
```
GT Quat:  [1.0000, 0.0000, 0.0000, 0.0000]  ← Identity (no rotation)
Accel:    [-20, 73, -8153] counts
Accel_Z:  -8153 counts ← NEGATIVE
Magnitude: 8153 counts ≈ 1g ✓
```

**Synthetic static_10s.csv (CORRECT):**
```
GT Quat:  [1.0000, 0.0000, 0.0000, 0.0000]  ← Identity (no rotation)
Accel:    [-20, 74, +8229] counts
Accel_Z:  +8229 counts ← POSITIVE
Magnitude: 8229 counts ≈ 1g ✓
```

**Expected Behavior (NED Frame):**
- Identity quaternion → Sensor aligned with world frame
- NED world gravity: `[0, 0, +9.81]` (down)
- Accelerometer measures **specific force** (reaction): `[0, 0, +1g]` (up)
- In counts: `[0, 0, +8230]`

**Actual Behavior (Realistic Data):**
- Accel_Z = **-8153** (pointing down, not up!)
- **WRONG SIGN** ✗

### Impact on Fusion

**When fusion algorithm processes this data:**

1. **Initialization** (sample 0):
   - Measures accel: `[0, 0, -1g]`
   - Interprets as: "Device is upside down"
   - Initializes orientation: 180° rotation
   - **Error**: 146° from true orientation

2. **Continued Processing**:
   - Tries to correct for perceived upside-down orientation
   - Gyro bias compensation diverges (2.97 dps)
   - Cannot recover from initial wrong orientation
   - **Mean error**: 58.6° across entire dataset

3. **Result**:
   - ❌ 100% of samples fail validation (error > 10°)
   - ❌ Unusable for algorithm testing
   - ❌ Misleading results

## Root Cause Analysis

### Where is the Bug?

**Suspect #1: IMUDataGenerator.generate_accelerometer()**

Location: `test/scripts/generate_synthetic_datasets.py` lines 189-214

```python
def generate_accelerometer(self, orientations, linear_accelerations, ...):
    # Line 196: Gravity vector in global frame (NED: pointing down)
    gravity_global = np.array([0, 0, self.spec.GRAVITY_MPS2])  # [0, 0, 9.81]

    for i in range(num_samples):
        # Line 200: Transform gravity to sensor frame
        gravity_sensor = orientations[i].inv().apply(gravity_global)

        # Line 203: Add linear acceleration (already in sensor frame)
        total_accel = gravity_sensor + linear_accelerations[i] * self.spec.GRAVITY_MPS2

        # ← BUG LIKELY HERE!
        # Should be: total_accel = -gravity_sensor + linear_accel
        # Accelerometer measures SPECIFIC FORCE (reaction to gravity), not gravity itself
```

**Physics:**
- Gravity force: `F_g = m * g` (downward)
- Accelerometer measures: `a = -g + a_linear` (specific force)
- The `-` sign is **missing**!

**Why synthetic data works:**
- Synthetic generator must have the correct sign somewhere
- Different motion profiles in `MotionScenario` class
- Possibly compensated elsewhere in the code

**Why realistic data fails:**
- Realistic motion profiles from `RealisticMotion` class
- Uses same `IMUDataGenerator.generate_accelerometer()`
- But motion initialization may differ
- Sign error manifests differently

### Hypothesis

**Possible Issue in `generate_realistic_motion.py`:**

The walking motion starts with:
```python
# Line 292
current_rot = R.identity()
```

But maybe the realistic motion generator has a different initialization or orientation convention that causes the sign flip.

**Alternatively:**
The bug might be in how `linear_accelerations` are computed in `RealisticMotion` class vs `MotionScenario` class.
